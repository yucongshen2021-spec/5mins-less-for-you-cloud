# 错误记录 — 帮你节省5分钟项目

> 此文按照全局 Rule 6 要求维护。每次开始任何修改前，必须先读此文件。
> 每个错误都记录了根因 + 避免方法。

---

## 1. Edit 工具"假成功"——改了但没存上

**现象**: Edit 工具返回成功，但文件实际未修改。多次在 release 分支发生，commit 后发现核心文件仍是旧代码。
**根因**: 在同一次对话中多次切换分支后，Edit 工具缓存的文件内容与实际磁盘内容不一致，old_string 匹配到了错误的版本。
**避免**:
  - 关键文件用 Write 覆写，不走 Edit。
  - 分支切换后，涉及端口/路径改动的文件，先用 Read 确认当前内容再 Edit。
  - 每次 commit 前用 `git show --name-status HEAD` 确认真的改了哪些文件。

## 2. 改了 process_manager 端口但忘了改子应用端口

**现象**: portal process_manager 改了端口后子应用起不来——因为 all_in_one / test_report / domain_capture 自己的 app.py 里也硬编码了端口。
**根因**: 端口不是单一配置源，分散在 process_manager.py、子应用 app.py、start_all.bat、测试文件中。
**避免**: 修改端口前，先 `grep -rn "旧端口号" .` 找到所有硬编码位置，列清单逐个改。改完再 grep 确认无遗漏。

## 3. PYTHONNOUSERSITE=1 全局生效导致所有 import 炸

**现象**: `start_all.bat` 启动后报 `ModuleNotFoundError: No module named 'markupsafe'`，所有 Flask 导入失败。
**根因**: `set PYTHONNOUSERSITE=1` 在 batch 文件第 4 行无条件执行。开发机用 `py -3` 时，flask 等依赖装在用户 site-packages（`AppData\Roaming\Python`），被这条禁用。
**避免**: `PYTHONNOUSERSITE=1` 只在便携 Python 路径存在时才设置（客户包场景），回退到 `py -3` 时不禁用。

## 4. 测试没跑 start_all.bat，只测了 py app.py

**现象**: smoke 测试全过，但用户双击 `start_all.bat` 就崩。用户说"是不是你做的测试都是自欺欺人的"。
**根因**: smoke 测试用 `py -3 app.py` 直接启动，绕过 batch 脚本的 PYTHONNOUSERSITE=1 问题。
**避免**: 涉及启动方式的修改后，必须用 `start_all.bat` 实际跑一次。不能只依赖 pytest。

## 5. Chrome 封禁端口 6000 没提前查

**现象**: Release 版设端口 6000，Chrome/Edge 直接拒连 `ERR_UNSAFE_PORT`。用户说打不开。
**根因**: Chrome 默认封禁包括 6000 (X11) 在内的几十个端口。没在选端口前查列表。
**避免**: 选端口前确认不在 Chrome blocked ports 列表中（常见被封: 6000, 6665-6669, 2049, 3659, 4045 等）。或者优先用 5000/7000/8000/9000 这些已知安全的。

## 6. 搞不清自己在哪个分支就改代码

**现象**: 在 main 分支编辑 release 文件，或者在 release 分支改了 demo 的 index.html。切分支后才发现改错了。
**根因**: 没有确认当前分支就开始编辑。
**避免**: 每次编辑 `application/portal/` 下的文件前，先 `git branch` 确认。改完检查 `git diff --stat` 确认改的是预期的文件。

## 7. Help 面板有 HTML/CSS 但没有 JS 绑定

**现象**: Release 版"?"按钮点了没反应。HTML 有 `helpOverlay` 面板和 `toggleHelp` 按钮，但 JS 里完全没有 `addEventListener`。
**根因**: 从 demo 同步 UI 时只复制了 HTML/CSS，漏了 JS 交互逻辑。
**避免**: 涉及 UI 交互的新元素，必须三步都检查：（1）HTML 元素存在、（2）CSS 存在、（3）JS 事件绑定存在。用 Playwright 实际点一下验证。

## 8. PowerShell Set-Content 写 JSON 带 BOM

**现象**: 用 PowerShell 写 `update_config.json`，`update_check.load_config()` 静默失败回退到默认配置。mirror_url 始终为空，更新检测不工作。
**根因**: `Set-Content -Encoding UTF8` 写入 UTF-8 with BOM。Python `json.load(encoding='utf-8')` 遇到 BOM 抛 `JSONDecodeError`，被 `try/except` 静默吞掉→用了默认空配置。
**避免**:
  - 写 JSON 用 `[System.IO.File]::WriteAllText($path, $json, [Text.UTF8Encoding]::new($false))` 避免 BOM。
  - `update_check.py` 中所有 `json.loads(path.read_text(encoding="utf-8"))` 改为 `encoding="utf-8-sig"` 兼容 BOM。

## 9. Commit 标题写"feat(release): port 6000-6004，有更新无下载"但实际没改代码

**现象**: `1cda2bd` 标题声称完成了 release 分支切换，`git show --name-status` 却只看到测试文件和工作流被改——app.py/process_manager.py/start_all.bat/index.html 一个没动。
**根因**: Edit 工具假成功（见错误 #1），加上提交前没有用 `git show --name-status` 验证。
**避免**: commit 前执行 `git diff --cached --name-status` 或 `git show --name-status HEAD`，确认改动的文件列表与预期一致。标题和内容不符的 commit 必须 amend 或追加修复。

## 10. 子应用反复重启——因为日志覆盖了错误输出

**现象**: domain_capture 和 test_report 不断重启（12 次），但日志里只有 "Serving Flask app" 没有 traceback。
**根因**: `stdout` 和 `stderr` 都重定向到同一个 log 文件，每次重启 `open(log_path, "a")` 追加。如果子 app 在 stdout 打印完 "Serving" 之后才崩溃，traceback 可能被缓冲或未及时 flush。
**避免**: 子应用异常时，直接去子应用的 app.py 目录手动运行 `py -3 app.py` 看完整输出。log 文件不代表全部错误。

## 11. 字体用了 DM Sans 而非 DESIGN.md 规定的 Inter

**现象**: Header 和 body 用的 `font-family: 'DM Sans'`，DESIGN.md 的 typography 规定用 CursorGothic（替代 Inter）。
**根因**: 直接从原来的框架 CSS 复制，没对照 DESIGN.md 检查字体。
**避免**: 任何 UI 修改前读 DESIGN.md typography 段。字体、颜色、间距、圆角必须和 DESIGN.md token 一致。

## 12. Header 背景白底而非 DESIGN.md 规定的 canvas

**现象**: `.topbar { background: var(--surface) }` 即白色 #ffffff，DESIGN.md `top-nav` 组件规定背景 `{colors.canvas}` 即 #f7f7f4 暖奶油色。
**根因**: 写 CSS 时习惯性用了 surface token，没对照组件规范。
**避免**: 改 UI 组件前，先在 DESIGN.md 的 `components:` 段查对应的组件规范。

## 13. 帮助面板内容写给开发者而非用户

**现象**: 帮助面板里写 `git checkout release`、`py -3 tools/build_release.py`、`pytest` 等开发命令。这是面向运维人员的工具，他们不需要知道 git。
**根因**: 我作为 AI 开发者的视角写文档，没有切换到终端用户（网络运维工程师）的视角。
**避免**: 写面向用户的文字前问自己：终端用户是谁（运维工程师）、他们需要知道什么（怎么生成配置、怎么梳理拓扑）、他们不需要知道什么（git、pytest、打包命令）。

## 14. 切分支后 pycache 导致跑旧代码

**现象**: 改了 app.py 但 portal 启动后还是旧行为（端口、import 都不对）。
**根因**: `__pycache__/*.pyc` 字节码文件比源码时间戳新，Python 直接用缓存跳过源码。
**避免**: 切分支后、改代码后，先删 `__pycache__` 再启动。或者在测试前统一 `find . -name __pycache__ -exec rm -rf {} +`。

## 15. 打 zip 时忘了自己在哪个分支

**现象**: 在 main 分支跑 `build_release.py` 打包，zip 里是 demo 版代码（没有 update_check import）。客户解压后 release 功能全废。
**根因**: 打包前没确认 `git branch`。
**避免**: 发布打包流程：先 `git checkout release`，确认 `git branch`，确认测试通过，再跑 `build_release.py`。

## 16. v1.0.1 manifest 没给 download_url，客户点不动"立即升级"

**现象**: release 第一版 `/api/update/manifest` 只返回 `version / release_url`，前端 JS 严守"必须有 download_url 才允许升级"的规则，导致客户能看到提示却点不动按钮。
**根因**: 原始设计里 download_url 由 GitHub release asset 提供，切到内网 mirror 后没补 zip 下载端点。
**避免**: 升级链路必须 4 步走通才算完成——`/api/update/check` → `/api/update/manifest`（含 download_url）→ `/api/update/download/latest.zip` → `/api/update/upgrade`。新加 `application/portal/test_update_manifest.py` 锁住该不变量。

## 17. build_release 重复打包 runtime/ 与 RELEASE_INFO.json

**现象**: 构建日志满屏 `UserWarning: Duplicate name: '帮你节省5分钟/runtime/...'` 和 `'帮你节省5分钟/RELEASE_INFO.json'`。
**根因**: 源码 walk 没排除 `runtime/`，runtime 又被 `collect_runtime_files` 单独收一遍；根目录 `RELEASE_INFO.json` 也没在 EXCLUDE_FILE_GLOBS，构建末尾再 `writestr` 一次。
**避免**: `EXCLUDE_DIR_NAMES` 必含 `"runtime"`，`EXCLUDE_FILE_GLOBS` 必含 `"RELEASE_INFO.json"`。`tools/test_build_release.py` 现在已经锁住这两个不变量，禁止再放回去。

## 18. 过早宣称"v1.0.1 主备 mirror 已生效"，本机端到端没跑

**现象**: 打包并 push v1.0.1 之后，本机 portal `/api/update/check` 实际返回 `config_error`（页面显示"无法检查更新"）。
**根因**: `--mirror-url` 只把主备源写入**客户包内**的 `update_config.json`；仓库根的同名文件仍是空 `mirror_urls`。本地运行 portal 用的是仓库版本，不是客户包内的版本。
**避免**: 改 update / manifest / build 链路时，必须 `curl /api/update/check?force=1` 拿到 `status: ok` 才能宣称"修好了"。开发机 portal 与客户包是**两份**配置，必须分别维护。

## 19. 开发机 portal 标题显示老版本（1.0.0），但客户包是 1.0.1

**现象**: 已发布 v1.0.1，客户包 `RELEASE_INFO.json` 是 1.0.1，但本机启动 portal 顶部显示 `v1.0.0`。
**根因**: 仓库根 `RELEASE_INFO.json` 是开发机运行时读的版本来源，构建脚本只往 zip 里写新值，不动源仓库的旧文件。
**避免**: 发新版必同步**三件**——客户包内的 RELEASE_INFO（构建写入）、仓库根 `RELEASE_INFO.json`（手工同步）、`application/portal/update_config.json`（手工填 mirror_urls）。

## 20. PowerShell 用 bash heredoc 提交 commit，整个命令报 ParserError

**现象**: `git commit -m "$(cat <<'EOF' ... EOF)"` 在 PowerShell 直接 `MissingFileSpecification`，commit 没生成。
**根因**: PowerShell 不解析 `$(...)` 子 shell，不识别 `<<` heredoc 语法。
**避免**: 写 commit message 一律用 `@'...'@` here-string + `Out-File -Encoding utf8` 写到临时文件，再 `git commit -F .commit_msg.tmp` + `Remove-Item .commit_msg.tmp`。

## 21. 写 commit message 留了 UTF-8 BOM，commit 标题首字符变隐形

**现象**: commit `7983679` 在 `git log --oneline` 看着像 `7983679 ﻿fix(release): ...`，subject 实际首字节是 `EF BB BF`（BOM）。
**根因**: 用 `Set-Content -Encoding UTF8` 写 commit message 文件，PowerShell 5.x 默认带 BOM。
**避免**: 写完 commit message 文件用 `Format-Hex` 看头三字节，确认是真正内容字节而不是 `EF BB BF`。优先用 Python 写文件。

## 22. 验证 portal 首页用 Invoke-WebRequest 30s 超时

**现象**: 改完 release 标题想看效果，`Invoke-WebRequest http://127.0.0.1:7000/` 卡住到超时退出。
**根因**: portal `/` 路由会同步遍历所有 sub-app 端口做健康检查，子应用慢/未起就拖死首页。
**避免**: 验证模板渲染内容（如标题版本号）用 Flask test client：`app.app.test_client().get("/")`。要看真实 HTTP 行为再起服务。

## 23. 中文 Content-Disposition 用 endswith 断言，全部失败

**现象**: 写下载端点测试时断言 `disposition.endswith('filename="帮你节省5分钟-1.0.1.zip"')` 一直失败，实际值是 `attachment; filename=5-1.0.1.zip; filename*=UTF-8''%E5%B8%AE...`。
**根因**: Werkzeug 按 RFC 5987 输出，非 ASCII 文件名走 `filename*=` 编码，ASCII fallback 名字会被裁。
**避免**: 文件下载断言一律走 RFC 5987：`f"filename*=UTF-8''{quote('帮你节省5分钟-1.0.1.zip')}" in disposition`。

## 24. update_check.py 的错误文案没提 mirror_urls

**现象**: 配置缺失时返回 `"未配置 github_repo 或 mirror_url"`，用户照着文案找 mirror_url 字段，但实际我把 schema 改成了 `mirror_urls`（list），用户去找新字段名找不到。
**根因**: 改 schema 时只动了实现，没同步错误文案。
**避免**: 改任何 config schema 时，同步搜全仓库 `rg <旧字段名>`，特别是 error message / 文档。

## 25. 给 mistake.txt 与 memory/ 选了不同载体，跨分支同步失败

**现象**: 我在 main 分支磁盘上把 9 条新错误追加到 log/mistake.txt 后 commit 了"git rm --cached"删除该文件。然后 git checkout release，磁盘上的 24 条被 release tracked 版本（15 条）覆盖，新追加内容丢失。
**根因**: 没意识到 git checkout 在切换分支时会用目标分支 tracked 的版本覆盖工作树。在 mistake.txt 转 local-only 之前先在 main 编辑了它。
**避免**: 把一份共享文档转成 local-only 时，第一步必须是先在所有相关分支都加 `.gitignore` + `git rm --cached` + commit；之后才允许写入新内容。否则磁盘版本会被另一个分支的 tracked 版本覆盖。

## 26. 客户 portal 与 mirror 共享 7000 端口，同台机器自我 loopback 必失败

**现象**: 用户解压 v1.0.1 zip 到桌面跑客户 portal（监听 0.0.0.0:7000），update_config 备源是 `http://192.168.5.10:7000/api/update/manifest`，但本机 IP 就是 5.10，于是 5.10:7000 = 客户自己。客户 portal 的 `/api/update/manifest` 扫本地 dist/，但客户包不含 dist/（构建脚本就要排除），返回 404，被 update_check 视为 mirror 失败。两源全失败 → `status: network_error` → "无法检查更新"。
**根因**: 架构混淆——客户 portal 同时承担"使用更新源"与"提供更新源"两个角色，共享 7000 端口。同台机器只能一个进程，客户和 mirror 必然冲突；即便不冲突，客户的 manifest 本身没数据可服务。
**避免**: mirror 必须是独立服务，独占自己端口（现选 8000），由 dev 机器上的 `tools/serve_mirror.py` 跑。客户 portal 删除 `/api/update/manifest` 与 `/api/update/download/latest.zip` 路由——客户只是 mirror 的 consumer，不再是 provider。验证时端到端起一份解压客户 + 一份独立 mirror，看 `/api/update/check?force=1` 必须返回 `status: ok` 才算修好。

## 27. 改 BUNDLE_NAME 时忘了同步 upgrade.py 里硬编码的 _BUNDLE_NAME

**现象**: build_release.py 改 BUNDLE_NAME 后客户解压目录变了，但 upgrade.py 里的 `_BUNDLE_NAME = "帮你节省5分钟"` 没改，会导致升级时备份/恢复路径错位、新版本启动指向不存在的目录、bat 模板里的 `{bundle}` 替换错误。
**根因**: 同一概念在两处独立硬编码（build_release.BUNDLE_NAME 与 upgrade._BUNDLE_NAME），改一处忘改另一处。
**避免**: 改 BUNDLE_NAME 时全仓库 `rg "帮你节省5分钟"` 列出所有命中点，逐个评估是文案、构建产物名还是 upgrade 路径前缀，一次性同步。注意：改名带来一次"v1.0.0 客户首次升级到新名字"的迁移问题（旧目录不会被覆盖、需手动删），从新名字开始才一致。

## 28. IPSec UI 按钮放进了 er5-panel-hk-us 共用面板，HK 也跟着出现按钮

**现象**: ER 5.0 IPSec 隧道类型按钮（OpenVPN/IPSec）放在 `<div id="er5-panel-hk-us">` 内，HK 与 US 共用同一个面板，导致选 HK 时也能看到 IPSec 按钮，而 HK IPSec 还没实现。
**根因**: 用 panel 复用结构装专属 us 的控件，没有在 showNetPanel 里按 variant 单独控制 `.er5-tunnel-type` 显隐；同时 getER5TunnelType 直接读 radio，切到 HK/4.0/flink 后 radio 仍可能是 ipsec，发请求时携带脏 tunnel_type。
**避免**: 控件可见性必须在 panel 切换函数（showNetPanel）里按 (tool, version, variant) 三元组明确判定，而不是依赖 panel 嵌套；getter 同步加防御逻辑：上下文不允许时直接返回安全默认值，且把 radio 强制重置以避免脏状态。

## 29. 默认路由 next-hop 把 0.0.0.0/0 写成 wan_gw，黑洞触发条件错位

**现象**: IPSec/OpenVPN 模板里 `set protocols static route 0.0.0.0/0 next-hop {wan_gw} distance '220'` + `set protocols static route 1.1.1.1/32 next-hop {wan_gw}`。这等于把 0/0 和 1.1.1.1 都直接指向 WAN 网关，绕过了"黑洞触发器"的设计意图。
**根因**: 不熟悉这套配置的语义就推断 next-hop 都用同一个值。线网原始 VyOS 是 `0.0.0.0/0 next-hop 1.1.1.1 distance 220`（distance 较高的备选默认路由，且 1.1.1.1 这个伪 IP 必须再被 1.1.1.1/32 → wan_gw 的另一条静态路由解析）——这是一种刻意制造的"必须有 wan_gw 才能用 default route"的依赖链路，触发条件解耦。
**避免**: 改任何 production VyOS 路由块前，先把原始线网 6-8 条相关 set 语句完整对照一遍；遇到看似冗余的中间跳（1.1.1.1/32 → wan_gw）不要"优化"，那是 trigger 设计的一部分。

## 30. 模板自定义只做扁平下拉，新增的 IPSec 模板加不进去也找不到

**现象**: 「我来定模板」用 `<select>` 单层下拉展示 _SCENARIO_LIST 全部 25 条；后续加 ER 4.0/5.0 IPSec 模板时，要么和 OpenVPN 同名混淆，要么只能拼接长串 key（"Epoch FastIP 5.0 · 非香港出口 · IPSec"），用户在 25 项里翻找。
**根因**: 数据结构与 UI 一对一映射成扁平 list；新增子分支（OpenVPN/IPSec、4.0/5.0）只能往 key 里继续叠 `·` 分隔的层级。
**避免**: 一开始就建立独立的 `_SCENARIO_TREE` 树形元数据 + `_scenario_tree_leaf_keys + _validate_scenario_tree` 启动期校验（保证树叶子和扁平 list 不漂移），UI 用级联下拉。新增 IPSec 这种正交维度时，只在树里加节点，扁平 list 也补一行，叶子 key 仍然是稳定字符串便于 disk alias / example 映射。

## 31. cascade menu 从引入第一天就有 bug，API 测试全过但用户看不到

**现象**: 「我来定模板」的 cascade menu 场景选择完全空白，4 个一级菜单项（Epoch FastIP / USG FastIP / Epoch MPLS / AR SD-WAN）都不显示。API 测试 16 个全绿。

**根因（两个 bug）**:

**避免**:
  1. 任何 UI 重构后，必须有至少一个 Playwright/browser-based 测试验证渲染结果——API 测试不能替代视觉验证。

## 49. make_report.py subprocess 继承了 stdin TTY → 非交互模式下 input() 阻塞崩溃

**现象**: 测试报告在 web 页面点击"开始生成报告"后，CE ping 测试失败时
make_report.py 崩溃：`EOFError: EOF when reading a line`。
触发链：ping 失败 → code != 0 → `sys.stdin.isatty()` 返回 True
（因为 subprocess 继承了 flask 进程的 stdin，而 flask 是从终端启动的）
→ `ask_on_failure()` → `input()` → 但 subprocess 的 stdin 已经被占用 → EOFError。

**根因**: `run_task_loop` 和 `ask_on_failure` 只检查 `sys.stdin.isatty()`
来判断是否交互模式，没有检查 `--no-manual-pause` 标志。
而 web app 通过 `subprocess.Popen` 启动 make_report.py 时，stdin 默认从
父进程继承（父进程如果是 terminal 启动的，isatty() 就返回 True）。

**修复**:
  1. 添加 `_INTERACTIVE` 全局标志，当 `--no-manual-pause` 或 `--smoke` 时设为 False
  2. `run_task_loop` 和 `ask_on_failure` 的 isatty 检查增加 `and _INTERACTIVE`
  3. app.py 的 Popen 增加 `stdin=subprocess.DEVNULL` 作为额外防护

**避免**:
  1. 任何用于 web 后台的 subprocess 必须同时设置 `stdin=subprocess.DEVNULL`
  2. 非交互标志不应只依赖 `sys.stdin.isatty()`，必须传参或设环境变量
  3. 举一反三：检查项目所有 subprocess.Popen 调用，确认 stdin 已重定向

**根因**: 只做了 mv 操作，没意识到 mv 只是换位置，内容仍是垃圾。一次性测试产物的生命周期：测试跑 → 产生 → 测试结束就没有保留价值。

**避免**:
  1. 移入 `temp/` 目录的一次性文件必须立即删除（`rm -rf temp/*`）
  2. `temp/` 是运行时测试的工作目录，git 里只保留 `.gitkeep` 占位
  3. 区分两类 temp 内容：**测试运行时产生**的子目录（一次性，不保留）和**测试代码本身**（在 `application/test/`，永久保留）

## 51. 宣称"测试报告可用"但只测了 API 没测浏览器 UI

**现象**: 用户点"开始生成报告"按钮后页面无反应，一直"运行中"无日志回显。
我用 `curl /api/run` 返回 `ok` 就声称"可用"，但用户是通过 portal 代理 (`/app/test_report/`)
访问的——完整路径是浏览器 → portal:7000 → proxy → :7002。

**根因**: portal 的 `proxy.py` 用 `with urlopen(...) as resp:` 的 `__exit__` 在
返回 `Response(generator)` 时就关闭了 HTTP 连接。Flask 后续迭代 generator 调用
`resp.readline()` 时连接已关 → 返回空 → 浏览器 EventSource 立即触发 `onerror`。

**修复**: SSE 响应不用 `with`，手动管理 `resp` 生命周期——generator 的 `finally` 块里
`resp.close()`，保证流未结束时连接不关。

**避免**:
  1. **任何涉及 UI 的功能必须以 Playwright 真实点击按钮验证**，不能只依赖 curl API。
     API 200 ≠ 用户看得到。
  2. `with urlopen(...) as resp:` 的 `__exit__` 在函数返回时就触发——如果 generator
     还没消费 `resp`，连接就关了。流式响应必须手动管理连接生命周期。
  3. 举一反三：检查 proxy.py 是否有其他使用 `with urlopen` + generator 的模式。

## 52. 反复用 curl API 测试就声称"修复完成"，从不打开浏览器看真实效果

**现象**: 用户三次指出 UI 问题——测试报告无回显、乱码、初始化错误——
我每次都先用 curl / Python urllib 测 API，看到 200 就回复"已验证通过"。
但实际上用户打开浏览器看到的是完全不同的结果：无日志、乱码、布局错误。

**根因**: 心理模型是"API 正确 → UI 正确"，但中间隔着 proxy 重写、SSE 流式、
编码转换、CSS 布局、JS 事件绑定等无数环节。API 只是后端，不是用户体验。

**避免**:
  1. **铁律：用 Playwright 模拟用户的行为，检测所有按钮和显示。**
     这句话必须刻在心里。curl 只用于快速诊断，绝不能作为"验证通过"的依据。
  2. 每次声称"修复完成"前，必须贴出 Playwright 验证结果——按钮点击、
     文字内容、控制台错误、布局状态。
  3. Playwright 测试要点：点击每个按钮 → 检查状态变化 → 读取显示文字
     → 检查无乱码 → 检查 CSS 布局（高度/溢出/z-index）→ 检查 console 无报错。
  4. 这条规则已写入 CLAUDE.md 规则 2，每次改 UI 前必读。

## 53. wanip_hosts 返回 (PE侧=奇数, CE侧=偶数)，AR 传统组网把 PE侧赋给了"本机"

**现象**: AR 传统组网的 GRE 隧道本机 IP 是奇数位（.237），但用户说"本机隧道 IP 应该是 /30 的偶数位"。

**根因**: `wanip_hosts(cidr)` 返回 `(hosts[0]=奇数=PE侧, hosts[1]=偶数=CE侧)`。
  `ar_traditional_v1.py` 写 `t_local, t_remote = wanip_hosts(wanip)`，按位置把 odd→local, even→remote。
  但 AR 路由器是 CE 侧设备，"本机" = CE 侧，应该拿偶数位 `hosts[1]`，不是奇数位 `hosts[0]`。
  函数 docstring 写了"PE 侧 / CE 侧"但调用者没有按语义解构，而是按位置直接赋值。

**修复**: `_pe_ip, _ce_ip = wanip_hosts(wanip); t_local = _ce_ip; t_remote = _pe_ip`

**避免**:
  1. `wanip_hosts` 这类带语义顺序的共享函数，调用时必须用带语义的变量名（`_pe_ip, _ce_ip`）
     而不是泛化名（`t_local, t_remote`），强迫自己思考谁是 PE 谁是 CE。
  2. 举一反三: ER FastIP (`pe_ip, ce_ip`)、MPLS (`pe_ip, ce_ip`)、AR SD-WAN (`wan_peer_ip, wan_ce_ip`)
     都正确使用了语义变量名——只有 AR 传统组网用了泛化变量名，这是 bug 的前兆信号。
