### 修复：访客点登录后「portal 套 portal」

- 问题: 子应用都跑在 portal 的 iframe 内，访客登录链接 `href="../../login"` 在 iframe 内打开登录页，登录成功 `window.location.href='/'` 把**整个 portal** 加载进 iframe，形成 portal 套 portal。
- 根因: ① 登录链接未跳出 iframe；② portal iframe 的 sandbox 无 top-navigation 权限，即便加 `target="_top"` 也会被静默拦截。真正高频触发点是**默认首选应用 all_in_one 的访客横幅**（访客一进来就看到它）。
- 文件: `application/usg_virus_test/templates/index.html`（编辑）
  - 说明: 全部 4 处登录链接（访客横幅 / 顶部 CTA / 清单锁定卡 / 下载卡）加 `target="_top"`。
- 文件: `application/all_in_one - cc/web/templates/index.html`（编辑）
  - 说明: 2 处访客横幅登录链接（guest-banner / tpl-admin-banner）加 `target="_top"`。这是默认应用，是用户实际踩到的主要路径。
- 文件: `application/portal/templates/index.html`（编辑，共享组件）
  - 说明: 两处 iframe sandbox（静态 `iframe_first` + 动态 `switchApp` 创建）追加 `allow-top-navigation-by-user-activation`。
  - **踩坑更正**: 初版误用 `allow-top-navigation-to-valid-origins`，Playwright 实测浏览器报 `'allow-top-navigation-to-valid-origins' is an invalid sandbox flag`（当前 Chromium 不识别该 token），整个 sandbox 解析失败、顶层导航全被拦，表现为「点登录没反应」。改用 `allow-top-navigation-by-user-activation`（有效、需用户手势——点击即满足、兼容性好）。
  - 双保险: 另在 portal 加 `window.addEventListener('message', ...)`，子应用 `postMessage({type:'nav-top',url})` 上来由父窗口（非 sandbox）代为顶层跳转，不依赖 sandbox token 也能工作。
- 文件: `application/usg_virus_test/templates/index.html` / `all_in_one .../index.html`（编辑）
  - 说明: 各加一段全局点击拦截——iframe 内点 `a[href$="/login"]` 时 `preventDefault` + `postMessage` 给父窗口跳 `/login`；非 iframe 环境走链接默认行为。
- 文件: `application/stats/templates/user_dashboard.html` / `admin.html` / `guest_login.html`（编辑）
  - 说明: 返回/登录跳转改 `window.self!==window.top` 时 `postMessage({type:'nav-top',url})`，否则 `window.location.href`。guest_login 同时删掉硬编码 `:5000`，改相对 `../../login`（自适应端口/域名）。
- 验证: Playwright 无头 Chromium 端到端实测（8000 与 5000 全绿）——访客 iframe 内点登录→顶层跳 `/login` 且无嵌套；登录成功→回顶层 portal；登录后切回 USG 页域名可见、zip 可下载。sandbox 解析报错消失。
- 已知权衡: 登录后落在 portal 首页 `/`，需手动再点应用（portal 登录重定向固定为 `/`，未做 `next` 回跳）。
- 教训: sandbox 顶层导航 token 各浏览器支持不一，**改动必须用真实浏览器验证**，不能只 curl 看 HTML（mistake.txt 同类：UI 交互须浏览器冒烟，curl 看不出 sandbox 拦截）。
- 未动: 已停用的 `自动做测试报告 - cc/mock.html` 的 `href="/"`（应用未运行；且该绝对路径会被 proxy 重写成 `/app/test_report/` 指回应用自身，不构成套娃）。

### USG 测病毒：工具包下载纳入统计（统计下载人数）

需求：统计有多少人下载了 USG 测病毒工具。难点：原下载按钮直连 GitHub archive，不经过本服务器，无法统计。改为下载走本应用代理，下载即落一条统计记录。

- 文件: `application/usg_virus_test/data/usg-virus-test.zip`（新增）
  - 说明: 工具包（exe + urls.txt + cs + ps1 + README，约 14 KB），由本机仓库 `~/usg-virus-test` 打包而来，供下载接口直接返回。
- 文件: `application/usg_virus_test/app.py`（编辑）
  - 说明: 新增 `GET /api/download`——仅登录用户（X-User-Id 非空，否则 403）；返回 zip（`Content-Disposition` 带 RFC 5987 中文文件名 `usg一键测病毒.zip`）；并**直接调用共享库 `common.stats_db.log_access()` 落一条记录**（app_id=usg_virus_test，function 经 derive_function 得「下载·USG测病毒工具」，带 username/ip）。
  - 为什么不走 proxy 的 generate 判定: proxy 的 `_try_log` 只记 `_GENERATE_PATTERNS` 白名单端点，且会把响应体当生成内容落库——zip 是二进制，落库会变乱码膨胀。故由应用自己写记录，proxy 层不重复记。
- 文件: `application/common/stats_db.py`（编辑）
  - 说明: `derive_function` 加 usg_virus_test 分支（`api/download`→「下载·USG测病毒工具」，根路径→「打开·USG测病毒」）。**未**加入 `_GENERATE_PATTERNS`（理由见上）。
- 文件: `application/usg_virus_test/templates/index.html`（编辑）
  - 说明: 两处下载按钮 href 由 GitHub archive 改为相对 `api/download`（经 proxy 注入的 `<base href="/app/usg_virus_test/">` 解析到 `/app/usg_virus_test/api/download`）；文案 zip 大小 20KB→14KB。GitHub 源码浏览链接保留。
- 验证（8000 + 5000 均过）:
  - 访客下载 → 403；登录下载 → 200 返回完整 zip（5 文件齐全，文件名 `usg一键测病毒.zip`）。
  - Playwright 实测点下载按钮：触发浏览器下载、页面不跳走、无 console 报错。
  - 下载后 `/app/stats/api/records?function=下载` 出现记录「下载·USG测病毒工具」+ 用户名。
- 说明: 下载记录计入 9000 看板「功能 Top10」与记录表（按 function=下载 可筛）；因当前下载量少（1-2 次）暂未进 Top10 榜单，量上去即显示。per-user「我的数据」仍只统计 `生成·%`（设计如此，下载不计入个人生成次数）。

### stats 看板：搜索框不生效（搜用户名搜不到）

- 现象: 9000 看板搜索栏搜用户名（如 `chin`/`chinq`）没反应。
- 根因: 不是搜索坏了——搜索功能本身正常（浏览器实测 20 行→按内容过滤正常）。真正问题是**搜索框 `q` 的 SQL 只查 path/data_header/response_body，不查 username**（placeholder 也只写「路径/数据头/生成内容」）。用户搜用户名时，该词只落在 username 字段→命中 0，像「没作用」。叠加因素：记录表后端默认只显 `function LIKE '生成·%'`（`_filters_from_args` 硬编码），非生成记录默认不可见。
- 排查: 直接查容器内 SQLite（注意 8000/5000 是两个独立库，数据不同）定位「chin」分布——username 10 条、response_body 9 条；旧 q 逻辑命中 9，搜完整用户名 `chinq` 命中 0。
- 文件: `application/common/stats_db.py`（编辑）
  - 说明: `_build_where` 的 `q` 过滤从 `(path OR data_header OR response_body)` 扩为 `(username OR path OR data_header OR response_body)`，参数同步 3→4 个。
- 文件: `application/stats/templates/index.html`（编辑）
  - 说明: 搜索框 placeholder 「路径/数据头/生成内容」→「用户名/路径/数据头/生成内容」。
- 验证（8000 + 5000）: 搜只在用户名出现的词（8000 用 kube、5000 用 chinq），旧逻辑命中 0、新逻辑命中对应用户全部生成记录；浏览器实测搜 chin 表格 20→17 行（chinq 用户 10 条 + 生成内容含 chin 9 条去重）。
- 未动: 「默认只显生成记录」的 `_filters_from_args` 逻辑保留（用户本次只要搜索含用户名，未要求放开记录类型）。
