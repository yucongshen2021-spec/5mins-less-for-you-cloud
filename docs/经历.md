运维同学每次给客户开线路，都要照着 LineID / PE / 隧道 / 出口 IP / 内网段，手抄一份几百行的网络配置。同样的内容一天敲几十遍，错一个字符整段就上不了线。

"每上一台新设备，光照着模板敲配置就要 5 分钟，还经常敲错。"

我想法很简单——把这 5 分钟省下来。项目名字就是这么来的。

---

## 四个桌面工具 → 一个 Web 应用

最开始写了四个独立的 tkinter 窗口程序：ER FastIP、USG FastIP、Epoch MPLS、AR SD-WAN。每个都是双击 .exe 就跑，填几个字段点生成，几百行配置出来，复制粘贴完事。

客户说原来 5 分钟的活现在 30 秒。

但问题也明显：四个图标四个界面，新人要学四遍；每个工具的默认参数和模板都写死在代码里，改一行要重新打包 exe；同一段 IP 计算逻辑在四个工具里写了四次，改一处漏三处。

我没有直接改桌面程序，而是在外面套了一层 Web。原来的窗口程序还能跑，但额外起了个本地 Flask 服务，把同样的逻辑暴露成网页。运维开浏览器访问 localhost 就行。

这一步意外地改变了很多东西——不用装四个 exe 了；整个产品有了统一的视觉（奶油底色、橙色按钮、统一字体）；复制配置、导出脚本、看示例全在一个页面里。

---

## 模板编辑器：不再什么都找作者

每个客户场景都有自己的习惯——香港出口和美国出口的隧道编号方式不同，MPLS 国内段和海外段的 BGP 团体值不同，有的客户还要求特定的注释行。

原来这些都写死在模板里，每次客户提需求，我得改源码、重新打包、重新发版本。这显然不长久。

加了一个模板编辑器：每个场景的模板暴露出来，运维直接在网页上改，保存后立刻生效，不用重启、不用找我、不用更新版本。

防改坏做了两层：一份只读的"出厂模板"，一份用户自己的"工作区版本"。一键就能回到出厂状态。

同期做了第一个 PyInstaller 打包：所有东西塞进一个 19MB 的 exe，客户机器上双击就起，自动开浏览器，不用装 Python。

## 最难熬的三天：WAN DHCP 联动 bug

WAN DHCP、旁挂模式、回程路由这三个开关之间有复杂的联动关系。Web 模式下出了一个极其隐蔽的错乱：用户只勾了"WAN DHCP"，生成出来的配置里 LAN 网段莫名其妙变成了 WAN 网段，LAN 接口消失了一半，DHCP 下发的子网也错了。

最折磨人的是它完全反直觉——WAN 相关的字段看着都没问题，偏偏 LAN 那边乱了。每次以为修好了，换一种组合又冒出新症状。

前两天一直在表层打补丁：怀疑模板渲染、怀疑参数注入、怀疑前端联动……每打一次补丁又冒出新的周边症状。第三天放下所有补丁，从头梳理了一遍状态管理。结论是开关之间的对应关系从一开始就错了，前面几次"修复"其实都是在错的基础上加新错。

修完根因之后又花了半天清理之前为了绕开 bug 写的所有补丁代码。后来这就成了一条习惯：临时绕过的代码，根因修好之后必须删掉。

然后把所有容易出错的组合写成了自动化测试。

## 让报错说人话

修完逻辑后发现另一个问题：报错全是英文和内部代号。运维填错字段看到的是 `Parser error: natmiss(['hkip'])`，只能截图来问我。

把所有面向用户的错误信息重写成中文短句：

- `Parser error: natmiss` → "数据头里缺少海外出口 IP，请检查 PE 配置块"
- `Builder not found` → "暂不支持该场景，请切换变体"
- `Scenario not found` → "该模板已被删除，请重置后重试"

改完之后报错截图问人的频率掉了大概 80%。

## 域名抓取工具的三次折腾

运维经常需要知道某个客户网站用了哪些子域名、哪些 CDN。原本只能开 F12 翻 Network 面板一行一行数。

先写了个命令行版本，被打回来了——"运维不会用命令行"。

又写了个 tkinter 桌面版，输入网址点一下就跑。但打包出来 228MB，因为塞了完整浏览器内核。

改了第三版：让它自动扫描用户电脑上已安装的浏览器——Chrome、Edge、360、QQ、搜狗、Brave……扫到就用，不再自带浏览器。打包瘦到 72MB。

后来又加了一层 DNS 链路追踪：跟着 CNAME 一直查到底，匹配几十种 CDN 服务商（百度云加速、腾讯云、网宿等），用可展开的树形界面展示完整跳转链路和 CDN 归属。

最后也搬进了浏览器，跟其他工具统一风格。

## 配置梳理：从文本到拓扑图

这是整个套件里我最满意的一个。

运维拿到客户现网的 VyOS 或华为防火墙配置，几百上千行，要在里面人肉数清楚：哪些是主线、哪些是备线、哪些归属不明；哪些走 GRE、哪些走 IPSec、哪些是 OpenVPN；每条线路的 SNAT 网段、默认路由出口。

原本是对着屏幕找半小时的活。

做了一个单 HTML 文件——双击打开，左边粘贴配置，点分析，右边出一张拓扑图。主线、备线、未知线路自动分三条车道；每种隧道自动配色（绿色 UPE、红色海外 NAT、紫色 IPsec、青色 BGP 邻居）；SNAT 网段标注在对应节点旁；默认路由用黄色徽章标出来。可缩放、可拖拽，50 个隧道的大客户也能看清楚。

关键是不用装任何东西——单 HTML 文件丢给客户现场的工程师，双击就能用。

主备线判定是最有意思的挑战。配置里有时在隧道描述里写了 "main"/"backup"，有时在 BGP 邻居命名里暗示，有时在路由 track 名称里隐含，有时这几处还互相矛盾——BGP 命名说是主线，但 track 名称又像是备线。

做了一个多源证据投票机制：把所有可能暗示主备的地方都解析出来，按可信度排序，冲突时标警告让用户确认，不静默猜测。

后来一位运维拿真实客户配置来测，跑出一条"未知线路"。他凭经验觉得应该是备线，我们一起翻原始配置，发现线索藏在一条 NAT 规则的描述里——机器没看到，人能看到。立刻补了一条证据来源：NAT 描述。

## 统一门户

到这时候套件里有 4 个独立工具，各跑在不同端口上。运维桌面上四个图标，浏览器里四个标签页。

做了一个统一门户：打开一个地址，左边 sidebar，右边是当前工具。启动一次所有子应用自动起来，哪个崩了门户自动拉起来，关了门户全部一起关。切换过的工具再打开是瞬间的，不需要重新加载。

这一步之后，从一组工具变成了一个产品。

## ER 5.0 适配

客户开始大规模部署新一代 ER 5.0 设备，整体切到了 VyOS 语法，命令行风格和老设备几乎是两个世界。

给配置生成工具加了一个 4.0/5.0 版本切换。最大的挑战不是技术——是确保新功能不破坏老功能：4.0 所有场景切到 5.0 再切回来必须完全一样；5.0 的界面布局、字段、提示和 4.0 保持一致；模板编辑器、默认值、示例数据全部要对齐。版本切换就像一个开关，点一下整个工具变了一代，但操作方式完全不变。

## 整理 & 测试

到 5 月 24 日，根目录已经有点乱了——5 个应用文件夹平铺，启动脚本、测试文件、临时截图散落各处。把所有应用搬进 `application/`，测试统一进 `application/test/`，临时文件清干净。

5 月 28 日整理了测试体系。迁移前几十个测试文件散落在各种角落，有几个根本跑不起来——浏览器自动化一启动就卡死（PIPE 缓冲打满）、pytest 收集就报错（缺 plugin）。还有 4 个应用从来没有任何测试。

修了三个基础设施问题：
- test_e2e 卡死：`Popen` 的 `stdout=PIPE` 缓冲打满阻塞了 Flask，改 `DEVNULL`
- pytest 跑 Playwright 报 `fixture 'page' not found`：缺 `pytest-playwright`，补了 conftest
- portal smoke 残留子进程污染后续测试：Windows 上 `terminate()` 不触发 `atexit`，用 `psutil` 按端口杀

给 4 个没测试的应用各补了最小烟雾测试：能启动、首页能访问、关键内容能找到。

最后跑了一遍——44 个 pytest + 42 个 Playwright E2E，全绿。

## 从桌面搬到云端

项目最早是四个 Windows 桌面程序，双击 exe 就跑。后来套了层 Web，再后来整个搬到了 Linux Docker。

搬到 Linux 第一件事就是干掉 tkinter。原来的业务模块里到处都是 `tk.Tk()`、`StringVar()`、`Entry.get()`——这些在没显示器的服务器上根本跑不起来。最开始用 Xvfb 虚拟显示器凑合，但 16 个 worker 同时抢一个 X11 显示器，动不动就死锁。

最后写了个 `tkinter_stub.py`——把 tkinter 所有类和方法都替换成纯 Python mock。`Entry.get()` 永远返回空字符串，逼着 builder 走 globals() 回退路径去读表单参数。没有 Tcl 解释器、没有 X11、没有 DISPLAY 环境变量，16 个 worker 各自独立跑，互不干扰。

这个 stub 模块大概是整个项目里最"脏"但又最关键的代码——脏是因为它在欺骗所有业务模块，让它们以为自己在 tkinter 环境里；关键是因为没有它整个项目就没法在 Docker 里跑。

## 16 个 worker 的并发血泪史

最初只有 1 个 worker。一个人用没问题，两个运维同时点生成就开始排队。加到 8 个 worker，好了一阵。后来 16 个人同时用，又炸了。

问题出在模板上。原来保存模板的时候会写回全局 namespace——`ns[slot] = tpl`。一个 worker 里只有一个 ns，用户 A 保存了自己的模板，用户 B 同一个 worker 上的生成结果就变了。

改了三天。最终方案：generate 永远从磁盘读模板（`_get_effective_template`），save/reset 只写磁盘文件，不碰 ns。每个用户有独立的 `data/users/<uid>/editor_workspace/` 目录。这样即使两个用户被分到同一个 worker，各自的模板也不会互相污染。

后来写了个 16 用户并发测试——注册 16 个账号，同时发 16 个不同参数的生成请求，检查每个输出里只有自己的 IP、没有别人的。第一次跑挂了，改了又跑，跑了又挂。最后一次全绿的时候，长舒一口气。

## 登录系统：从"双击就用"到"请先登录"

搬到公网之后就不能"双击就用"了——任何人打开 IP 就能看到所有客户的配置数据。

做了登录系统：注册、登录、重置密码。又做了工作区隔离——每个用户只能看到自己的模板和生成记录。管理员 yucs 可以管理所有用户，普通用户只能管自己。

访客可以进来逛——看看界面长什么样——但所有按钮都是灰的。生成配置、复制、导出、填写示例、备注、模板编辑器，24 个按钮在 HTML 层面就 disabled 了，不依赖 JavaScript 执行。

有个坑特别折腾：按钮的 disabled 状态一开始只靠 JS 设置——页面加载时跑一个 `updateTemplateAdminUI()` 函数。但 all_in_one 是在 portal 的 iframe 里加载的，有时候 JS 来不及执行按钮就亮着。用户说"我用无痕模式进去按钮还是能点"，查了半天才发现是 HTML 层面没加 disabled 属性。后来用 Jinja2 模板条件渲染，访客时 HTML 里直接写死 disabled，JS 只负责登录后"移除"disabled。

## 后台和数据看板

做了个 9000 端口的统计看板。管理员能看到所有人的生成记录——什么时候生成的、什么场景、花了多久、数据头是什么、生成的配置内容是什么。普通用户只能看自己的。

管理员还能管理用户——重置密码、删除用户。yucs 不能被删。所有操作写审计日志。

有个细节花了不少时间：时间。容器默认时区是 UTC，SQLite 的 `datetime('now')` 也是 UTC。用户看到的创建时间比实际早 8 小时。改了容器时区、改了 SQLite 查询、还改了老数据的读取逻辑——读出来加 8 小时再返回。新用户注册时显式写 `datetime('now', '+8 hours')`，不依赖表的 DEFAULT 值（SQLite 的 ALTER TABLE 不更新已有 DEFAULT）。

只记录生成配置的请求，其他操作（切换页签、加载模板、预览）不记录。`test` 和 `ctest` 开头的测试账号也不记录。

## ER MPLS 海外：主线只要一个 vtun

某天用户在 9000 看板翻记录，翻到 996 条 ER MPLS 海外配置，皱了眉头：「主线不应该有 tunnel，只要一个 vtun 就能接。」这是设计--海外的主线是 OpenVPN 直连，不带 GRE 隧道；国内才用 GRE+VPN 的组合。

去生成一份看了下，确实问题大了。模板里把主线 GRE 隧道那 8 行 `set interfaces tunnel {main_gre_tun} ...` 写死了，海外主线是 `vtun_only`，`main_gre_tun` 是空的，于是输出里冒出 `set interfaces tunnel  address '/30'` 这种残废行--`tun1030` 没了，地址也没了，配置贴上去设备直接报错。连带 `set firewall options interface  adjust-mss`、`set track name  failure-count`、`set protocols static route ... next-hop  track `，全是空的。

根因是历史包袱：桌面版的 `generate_mpls_config` 用 `_build_gre_section` / `_build_vtun_section` 做条件渲染，GRE 为空就跳过--逻辑是对的。但后来改 Web 时把配置搬成字符串模板 `TEMPLATE_MPLS_OVERSEAS`，直接写死占位符，丢了那个「空就跳过」的判断。国内模板同样的问题，只是国内数据头里主线带 GRE，所以一直没暴露。

修法是给模板加块占位符。新增 `_mpls_compute_section_blocks(d)`，在 `build_*_format_dict` 里把 `{main_gre_section}`、`{bk_gre_section}`、`{main_vtun_section}`、`{bk_vtun_section}`、`{gre_fw_mss_block}`、`{main_track_block}`、`{mpls_static_routes_block}` 这些块预计算好--GRE 为空就返回空字符串，静态路由的 `next-hop` 和 `track` 名字按 `line_type` 走（`vtun_only` 用 `vtun_remote` 当 PE IP、`vtun_id` 当 track 名，跟桌面版 `generate_mpls_config` 里 `m_pe_ip`/`m_tun` 的逻辑对齐）。模板里把原来那一坨写死的行换成这些块占位符。

顺手把 `_mpls_compute_track_names` 也修了：原来 GRE 为空时 `{px}_track` 直接是空字符串，现在 `vtun_only` 也能从 `vtun_id` 派生 track 名。不过最后渲染时 `main_track_block` 用的是 `m_tun`（vtun_id 原值），跟桌面版一致，`{px}_track` 只是个备用字段。

改完同步磁盘 tpl 文件（`data/editor_defaults/ER_MPLS___海外配置/` 和 `国内配置/`），重建 8000 容器，跑全量测试 185/185 通过。再去看海外输出，主线只剩 `set interfaces openvpn vtun1104 ...` 那一段，`set interfaces tunnel` 只有备线的 `tun1618`，干净了。

## 踩过的坑

所有坑都记录在 `log/mistake.txt` 里（最初 8 个，截至 2026-07-20 已累积到 68 条，仍在持续追加）：

1. 磁盘模板和源码不同步--改了源码忘了同步磁盘文件
2. load 接口污染全局状态--只读接口不该改全局变量
3. reset 接口改全局 ns--多用户共享的 namespace 被污染
4. factory 快照在测试环境为空--import 时没自动初始化
5. 两个场景不读磁盘模板--用了模块变量而非磁盘读取
6. 访客按钮 disabled 依赖 JS--必须在 HTML 层面设置
7. 用户创建时间时区不对--SQLite 的 DEFAULT 不可靠
8. Agent 不读 mistake.txt 就改代码--每次第一步必须读指引文档

第 8 条是写给自己的。每次有新 agent（或者自己）接手项目，第一件事应该是读约束文件。不读就动手，一定会踩已有记录的坑。

项目现在有三层约束文件（都在 `docs/` 下，优先级从高到低）：

- **`docs/AGENTS.md`**（项目级工程守则）--架构/端口/鉴权/测试命令/部署/删除铁律/git push 修复。优先级最高，覆盖下面两层。
- **`docs/GLOBAL_RULES.md`**（全局规则层）--9 条通用规则（不猜测/Plan/日志/mistake/测试/DESIGN 等），跨项目共享，项目 AGENTS.md 优先于它。
- **`docs/DESIGN.md`**（UI 设计规范）--以 `all_in_one - cc/web/templates/index.html:9-28` 的 `:root` 为真相来源，约束颜色/字体/组件。UI 改动必读。

加上 `log/mistake.txt`（68 条历史踩坑，跨日期复用）。这套体系是 2026-07-20 整理成型的，之前只有单层 AGENTS.md。
