# 全局规则（Global Rules）

> 版本: v2.0 ｜ 最后更新: 2026-07-20
> 适用范围: 仅适用于 AI 协助编辑的代码、配置与文档。用户完全手写的部分不强制覆盖。
> 本文件是跨项目共享的「全局规则层」。项目级规则（如 `/opt/fivemins/docs/AGENTS.md`）优先级高于本文件。

## 优先级与豁免

规则冲突时按以下优先级裁决（高 -> 低）：

1. 用户当前轮的明确指令
2. 项目级 `AGENTS.md` / `CLAUDE.md` 等本地规则
3. 本全局规则

**轻量场景豁免**: 一次性脚本、实验性原型、紧急热修复可豁免 Rule 3（Plan）与 Rule 8（端到端测试），但 Rule 1（不猜测）、Rule 4（日志）、Rule 6（查 mistake）仍必须遵守。豁免须在回复中声明。

> 关于本仓库（monorepo）路径约定：仓库根为 `/opt/fivemins`，下有多个子应用（如 `application/all_in_one - cc`）。
> - **`mistake.txt` 仓库根共享**：统一在 `/opt/fivemins/log/mistake.txt`，跨子项目复用，不在各子应用 `log/` 下重复建。
> - **每日修改日志（`log/YYYY-MM-DD.md`）**：写在被改动的那一层；改子应用就写子应用 `log/`，跨子应用/根级改动写仓库根 `/opt/fivemins/log/`。
> - **plan/**：同理，写在改动所在层。

## 一、编码原则

### Rule 1: 禁止猜测意图，允许基于契约的容错

- **禁止猜测的是**: 用户业务意图、需求语义、数据含义、代码行为假设。
- **允许的是**: 基于明确契约的容错（如配置缺失用文档化默认值、网络重试、空值保护），这不属于"兜底"。
- **遇到不确定时按分级处理**:
  - 影响不可逆 / 外发动作（删除、推送、发布）-> **必须停下来询问**
  - 涉及用户偏好或多种合理方案 -> **必须询问**
  - 存在行业通用默认且可逆 -> 可自主决定，但须在回复中说明所用默认

❌ 反例: 用户说"加个登录"，自行假设要 OAuth + JWT + Redis session，直接实现。
✅ 正例: 用户说"加个登录"，先问认证方式、用户存储、是否需要第三方登录。

### Rule 5: 交付前自检（checklist）

每次交付代码前，按以下清单自检（从客户真实使用角度）：

- [ ] 主业务路径能否走通？异常分支是否处理？
- [ ] 错误信息对用户是否可读、可操作？
- [ ] 是否影响现有功能（回归）？
- [ ] 是否有越权、数据泄漏、硬编码密钥？
- [ ] 是否符合 Rule 1（无猜测）与 Rule 9（同类已排查）？

### Rule 9: 举一反三（排查清单）

被指出一个错误后，按以下顺序系统性排查同类问题，不得只修单点：

1. 当前文件中的同类函数 / 分支
2. 同模块、同模式的其它代码
3. 其它版本 / 分支 / demo 环境
4. 依赖该代码的调用方
5. 排查结果在回复中说明（即使结论是"无同类问题"）

## 二、流程规范

### Rule 3: Plan 文件保存在项目 `plan/` 目录

- Plan 文件路径: `<project>/plan/<feature-name>.md`
- `plan/` 不存在则先创建目录再写入
- 禁止放在项目外部（如 `~/.Codex/plans/`）

### Rule 4: 修改日志

- 每次代码修改后，在项目 `log/YYYY-MM-DD.md` 记录（`log/` 不存在则创建）。
- 同一天多次修改：追加到当天日期文件的 `### 时间戳` 子节点下，不新建文件、不新建日期章节。
- 每条记录含: 时间戳、文件路径、做了什么、为什么。
- 格式:

  ```markdown
  ## 2026-07-20

  ### 14:30
  - 文件: `capture_domains.py`
  - 说明: 创建脚本，使用 Playwright 抓取网页所有请求域名（新增域名采集能力）
  ```

> 修改日志（按日期，`log/YYYY-MM-DD.md`）与历史错误教训（跨日期复用，`log/mistake.txt`）同在 `log/` 下，但用途不同，不要混淆。

### Rule 6: 动手前先查 `log/mistake.txt`

- 任何修改前，先读**仓库根** `log/mistake.txt`（monorepo 跨子项目共享；本仓库即 `/opt/fivemins/log/mistake.txt`，不存在视为无历史错误）。
- 每次被用户指出错误后，立即按以下格式追加一条记录，供后续避免重犯:

  ```markdown
  ## <序号>. <一句话标题>

  **现象**: 简述发生了什么
  **根因**: 为什么会犯
  **避免**: 下次如何不重犯（必要时加 **修复**: 已做了什么）
  ```

  > 格式以本仓库现有 68 条记录为准（编号标题 + 现象/根因/避免）。条目按序号递增，不要用日期做标题。

## 三、测试规范

### Rule 7: 测试隔离目录

- 测试代码放专门目录，不污染现有代码。
- 命名约定: `test_<功能名>/`（如 `test_login/`、`test_upload/`）。
- 若项目已有客户的 `test/` 且内容不符，用 `test_<功能名>/` 区分，不覆盖客户测试。

### Rule 8: 端到端真实测试（用户体验优先）

核心原则: **API / 单元测试全绿 ≠ 用户能用**。必须有用真实用户操作路径的端到端测试。

- **含 Web/UI 的项目**: 用 Playwright 模拟真实点击，验证完整操作路径。
- **CLI / 库 / 数据脚本等非 UI 项目**: 用对应类型的端到端测试（CLI 用集成调用、库用调用方示例、脚本用真实输入跑通）。
- 必须验证:
  - 交互有响应（按钮点击 / 命令执行）
  - 业务逻辑正确、结果符合预期
  - 无文字 / 内容被遮盖（UI 项目）
  - 无布局错乱、溢出、z-index 冲突（UI 项目）

> 项目级细化优先于本条。本项目（all_in_one）的端到端定义见 `/opt/fivemins/docs/AGENTS.md`「测试」段。

## 四、领域规范

### Rule 2: UI 修改参考 `DESIGN.md`

- **触发条件**: 涉及颜色、间距、字体、布局、交互模式的修改。
- **不强制触发**: 纯文本内容修改、变量 / 类名重命名等不影响视觉的改动（但仍应顺带检查 `DESIGN.md` 是否有相关约定）。
- 项目无 `DESIGN.md` 时，提醒用户创建或询问 UI 偏好。
- 实现必须与 `DESIGN.md` 的颜色、间距、字体、交互模式一致。
